# QQ 农场飞牛 NAS 部署与变更说明

**应用名称：** QQ 农场  
**目标平台：** 飞牛 fnOS（x86）  
**当前版本：** `2026.10.22`（版本号 = 构建日期，同一天再发依次加 .1、.2……，见第 5.1 节）  
**服务端口：** 无（仅飞牛统一网关 Unix Socket）  
**运行环境：** 内置（Node.js v22.23.3 单文件可执行程序），不依赖应用中心 Node.js  
**上游版本：** 同步至 [liyangpengs/qq-farm-bot](https://github.com/liyangpengs/qq-farm-bot) `c6e2228`，合并提交 `25b0641`；安装包构建自 `632224f`  
**维护日期：** 2026-10-21

## 1. 部署目标

V1.1.0 将 QQ 农场从 Docker 应用改为**飞牛原生应用**：

- 不再使用 Docker 镜像和容器。
- 不再开放 `3007` 或任何其他 TCP 端口。
- 只能通过飞牛应用中心的统一网关入口访问：

`/app/qq-farm-bot/`

访问前必须先登录飞牛；应用自身不再有独立的管理员账号、登录页和密码。

## 2. 应用运行配置

| 项目 | 配置 |
| --- | --- |
| 应用标识（appname） | `qq-farm-bot` |
| 运行方式 | 飞牛原生进程：单文件可执行程序 `server/bin/qq-farm-bot`（Node SEA） |
| 运行环境 | 内置官方 Node.js v22.23.3 linux-x64（要求 glibc ≥ 2.28，飞牛基于 Debian 12，glibc 2.36）；**不依赖**应用中心 Node.js |
| 运行用户 | 生命周期脚本以 root 执行，服务进程通过 `runuser` 降权为应用用户 `qq-farm-bot` |

| 飞牛应用入口 | `/app/qq-farm-bot/`（`gatewayPrefix=/app/qq-farm-bot`，`gatewaySocket=app.sock`） |
| 访问控制 | 飞牛登录态 + 仅飞牛管理员（`X-Trim-Isadmin`），桌面图标 `allUsers=false` |
| 时区 | `Asia/Shanghai` |
| 数据目录 | `${TRIM_PKGVAR}/data`（`/vol*/@appdata/qq-farm-bot/data`） |
| 业务日志 | `${TRIM_PKGVAR}/data/logs` |
| 进程日志 | `${TRIM_PKGVAR}/app.log`（超过 10 MB 启动时轮转为 `app.log.1`） |
| 最低系统版本 | fnOS `1.1.3100`（统一网关要求） |

## 3. V1.1.0 功能性修改

### 3.1 改为原生应用，去掉 Docker 与端口

- V1.2.0 起后端为单文件可执行程序 `server/bin/qq-farm-bot`（见第 5 节 V1.2.0），前端为 `server/web/dist`，游戏配置、图片、proto、wasm 在 `server/resources/`。
- `cmd/main` 负责 `start / stop / status`：启动前检查可执行文件是否完整，启动后等待 Socket 就绪；停止时先 `TERM`，15 秒后 `KILL`，并清理 Socket 与 PID 文件。
- 后端新增 `QQ_FARM_SOCKET`：设置后服务**只**监听该 Unix Socket，不再调用任何 TCP 监听。
- 原 V1.0 容器内的 Unix Socket 代理已删除：飞牛网关直接连到应用自己的 Socket。
- 未设置 `QQ_FARM_SOCKET`（源码开发）时，默认只绑定 `127.0.0.1:3007`。
- V1.1.1 起，飞牛原生包**在任何情况下都不会监听 TCP**：`cmd/main` 额外设置 `QQ_FARM_NO_TCP=1`，打包时还会写入标记文件 `server/core/FNOS_NATIVE`；两者任一存在时，若缺少 `QQ_FARM_SOCKET`，服务记录错误并直接退出，而不是回退到 `3007`。

### 3.2 飞牛网关适配（沿用 V1.0 思路并改为原生实现）

飞牛网关转发请求时保留 `/app/qq-farm-bot` 前缀：

- 后端入口统一剥离前缀，原有路由无需改动；`/app/qq-farm-bot` 会 301 到 `/app/qq-farm-bot/`。
- Socket.IO 路径：`/app/qq-farm-bot/socket.io`。
- 前端构建使用 `VITE_BASE=/app/qq-farm-bot/`：静态资源、Vue Router 基路径、Axios `baseURL` 都带网关前缀。
  - 与 V1.0 的相对资源路径（`./`）相比，绝对前缀在多级路由直接刷新时也不会白屏。
- 前端 `gatewayPath()`：变异作物图、活动资源、星砂说明图、宠物日记默认图。
- 后端 `gatewayPath()`：种子/道具图、土地等级图（`/land-assets/*.png`）、宠物日记资源。
- 微信扫码二维码继续通过 Axios 请求 `/api/wx-login/tasks/<task-id>/qr` 后转为 `blob:` URL 显示。

### 3.3 移除管理员登录与改密模块

访问控制已完全交给飞牛，不再需要 `DISABLE_ADMIN_AUTH` 开关，相关代码整体删除：

- 前端：删除登录页 `Login.vue`、用户 store、侧栏「退出登录」菜单与「我的 Token」区块、设置页「修改管理员密码」卡片、路由登录守卫和 401 跳转。旧地址 `/login` 直接重定向到首页。
- 后端：删除 `/api/login`、`/api/logout`、`/api/user/change-password`、`/api/user/me`、`/api/auth/validate`，删除令牌校验中间件、Socket.IO 令牌校验、`admin-store` 与 `auth-security`（登录限流）模块。
- 侧栏用户卡片改为显示当前飞牛用户（来自网关 Header，`/api/fnos/me`）。
- 默认仅允许飞牛管理员访问（HTTP 返回 403，Socket.IO 拒绝连接）；如需让普通飞牛用户使用，可把环境变量 `QQ_FARM_ADMIN_ONLY` 改为 `0` 并把桌面入口 `allUsers` 改为 `true` 后重新打包。
- 旧数据中的 `admin.json`、`login-attempts.json` 迁移时改名为 `*.unused` 保留，不再读取。

## 4. 数据迁移（从 V1.0.x Docker 版升级）

覆盖安装时：

1. `upgrade_init`：若存在并运行着旧容器 `qq-farm-bot`，执行 `docker stop`，并把其重启策略改为 `no`，避免旧容器继续占用 `3007`。**不删除容器和数据卷。**
2. `upgrade_callback`：若新数据目录还没有数据，则：
   - 通过 `docker volume inspect` 找到 `qq-farm-data`、`qq-farm-logs` 的实际路径（找不到时依次尝试 `/var/lib/docker/volumes`、`/vol*/docker/volumes`、`/vol*/@docker/volumes`）；
   - `cp -a` 复制到 `${TRIM_PKGVAR}/data` 与 `${TRIM_PKGVAR}/data/logs`；
   - 写入标记文件 `${TRIM_PKGVAR}/data/.migrated-from-docker`（记录来源路径），之后不会重复迁移。
3. 先卸载 Docker 版、再全新安装本版时，`install_callback` 也会执行同样的迁移。

确认新版本账号与配置都正常后，可手动清理旧 Docker 资源（可选）：

```bash
docker rm qq-farm-bot
docker volume rm qq-farm-data qq-farm-logs
```

> 若迁移失败或找不到数据卷，应用会按全新安装启动，原数据卷保持不变；可把卷中的文件手动复制到 `/vol*/@appdata/qq-farm-bot/data/` 后重启应用。

### V1.2.0 / 内部升级号 2026.10.6

**目标：** 安装包自带运行环境，不再依赖飞牛应用中心的「Node.js v22」（`nodejs_v22`）。

**依赖检查：**

- 生产依赖全部是纯 JS，没有原生模块：
  - 包括 express、socket.io、ws、axios、protobufjs、winston、pushoo、node-fetch、long；
  - 没有 `.node` 文件、`binding.gyp`，也不涉及 better-sqlite3、sharp 等。
- ws 的可选加速模块 `bufferutil` / `utf-8-validate`、node-fetch 的可选 `encoding` 在运行时用 `try/catch` 加载，打包时设为 external，缺失时自动回退纯 JS。
- 影响打包的写法：
  - `client.ts` 用模板字符串动态 `require` 入口。改为新增 `fnos/sea/entry.js`，用静态 `require`。
  - 账号运行在 `worker_threads` 中，需要单独的脚本文件（进程模式下用 `fork`）。
  - 资源路径依赖 `__dirname`。
  - 所有 TSDK 加解密都在运行时读取 `.wasm` 文件。

**方案：Node SEA（单文件可执行程序）**

- 打包流程（见 `fnos/sea/build-sea.sh`）：
  1. 下载官方 Node.js `v22.23.3` linux-x64，按 `SHASUMS256.txt` 校验；
  2. 用 esbuild 把后端打包成一个 CJS 文件；
  3. 用 `--experimental-sea-config` 生成 blob，再用 `postject` 注入官方二进制，得到 `server/bin/qq-farm-bot`。
- 账号 worker 单独打包为 `server/bin/worker.js`，由可执行文件用 `worker_threads` 加载。进程模式（`FARM_RUNTIME_MODE=process`）下，可执行文件以 `FARM_WORKER=1` 重新启动自身。
- 静态资源以普通文件放在可执行文件旁边：
  - `server/resources/`：gameConfig 与图片、proto、tsdk wasm；
  - `server/web/dist/`。
- `runtime-paths` 能识别 SEA 并按上述目录取资源。也可以用 `QQ_FARM_RESOURCE_DIR` / `QQ_FARM_WEB_DIR` / `QQ_FARM_WORKER_SCRIPT` 显式指定，`cmd/main` 会全部传入。
- 可执行文件内置 `QQ_FARM_NO_TCP=1`。即使环境变量和 `FNOS_NATIVE` 标记文件都不存在，缺少 Socket 配置时也会直接退出，绝不监听 TCP。
- 为什么不直接内置 `app/bin/node` 加 `node_modules`：两种方案体积相近，SEA 文件更少，并且可执行文件自带「禁止 TCP」限制，因此选择 SEA。如果日后遇到 SEA 不兼容的依赖，可以回退为内置 Node 方案。
- 兼容性：官方二进制最高需要 `GLIBC_2.28`、`GLIBCXX_3.4.21`。飞牛基于 Debian 12（glibc 2.36、libstdc++ 12），满足要求。

**其他修改：**

- `manifest` 删除 `install_dep_apps = nodejs_v22`。
- `cmd/main` 删除 Node 查找，直接通过 `runuser` 以应用用户启动 `server/bin/qq-farm-bot`。
- 统计数据（`stats/<账号>.json`）默认存到数据目录 `QQ_FARM_DATA_DIR`。V1.1.x 原生版会尝试写入只读的安装目录。
- 已安装的「Node.js v22」应用不会被自动卸载。本应用不再使用它，如没有其他应用依赖，可以自行卸载。
- 体积：
  - FPK 由约 22.9 MB 增加到约 62.6 MB，安装后约 149 MB；
  - 其中可执行文件约 124 MB，主要是 Node.js 运行时本身；
  - `resources` 约 21 MB，`web` 约 3.4 MB。

#### 工作事项是什么（协议依据与语义）

- **工作事项是员工为雇主做的一次互动**，在被雇佣账号的「我的工作」页面提交，**不是**雇主给员工派活。雇主一方没有工作事项可做，只能在员工位上看到员工做了什么（`MilkTeaSlotView.interact_type / interact_at`）。
- 读取：`ActivityService.Operate`，活动 `2026110101`，操作号 63 `milk_tea_get_work_page`。返回 `MilkTeaGetWorkPageRsp`，包含 `my_shift`（雇主、班次 ID、起止时间、`interact_count / interact_limit`、`interact_previews`）、`interact_done` 和工资单 `slips`。
- 提交：操作号 65 `milk_tea_interact`。请求为 `MilkTeaInteractReq{target_gid=雇主 gid, interaction_type}`，返回 `MilkTeaInteractRsp{success, items_gained, wage_adjusted, owner, friend.bonus_amount, ...}`。
- 五种事项来自官方配置 `MilkTeaInteractionType`：
  1. 宣传推广：帮老板立即卖出 N 杯，员工得本班工资 20% 奖金；
  2. 花式摇杯：老板 3 小时奶茶券收益 +10%，员工得 30% 奖金；
  3. 招牌试饮：老板 2 小时收益 +20%，员工随机得 N 杯高级奶茶；
  4. 划水摸鱼：40% 概率得宣传喇叭，60% 概率工资减半；
  5. 申请涨薪：60% 概率工资翻倍，40% 概率工资减半。
- 限制：每个班次 `interact_limit` 次（采样为 1 次），`interact_done` 后不能再交；班次结束后、结算期不能交；本账号的奶茶店必须已开业（上游 `perform` 要求）。提交前上游会复核班次 ID、剩余次数、结束时间和事项数据完整性（宣传推广、招牌试饮的杯数缺失时不能提交）。
- 奖励：奖金并入工资，班次结束后通过工资领取（操作号 64 `milk_tea_claim_wages`）。本次**未**自动领工资（不在需求内）。

### 2026.10.20.3

**提交：** `f01dea5`。紧急修复：**2026.10.20.1 / 2026.10.20.2 中「大号/小号」「奶茶活动自动雇佣」在运行中的账号里完全没有生效**。请从这两个版本升级。

**用户反馈：** 「我用花费催熟了一个植物，也没等大号偷呢，小号就自己采了」。NAS 证据：

- `store.json` 里小号（账号 2）已经保存了 `fnosAltAccount={enabled:true, masterGid:1280585737, timeoutMinutes:10}`，两个账号都开了奶茶雇佣。

- 事发时：手动施肥 → 土地推送 → 巡田「收获完成 1 块土地 landIds:[15]」，中间没有任何小号判定日志。

#### 根因

- **主要原因：两个功能在 worker 里读不到设置。** 它们读设置时调用了 `require('models/store').getAccountConfigSnapshot()`，但 `models/store` 根本不导出这个函数，只有内部文件 `account-config.ts` 里有。调用就抛 `TypeError`。
  - 大号/小号：读取函数的 `try/catch` 吞掉异常，返回默认值「未开启」。所以小号每次都按普通账号收获，也不打印任何日志。
  - 奶茶：定时任务外层的 `.catch(() => null)` 把异常吞掉，所以从没雇过人，也没有日志。
- **设置下发本身是正常的。** 运行中保存时，主进程把完整配置发给 worker（`applyRuntimeConfigSnapshot`），worker 也确认收到了（界面提示「已保存」，而不是「账号未运行」）。问题只在两个功能读设置的方式不对。
- **单元测试没发现，是因为测试的 mock 写错了。** 2026.10.20.1 的测试用 mock 的 store 提供了这个并不存在的函数，所以测试全部通过。本版新增的回归测试用真实 store；把修复撤回、换回旧的读取方式时，6 个新测试全部失败。
- **收获路径本身没有绕过过滤。** 已逐个检查所有会自动收自己地的入口：
  - 定时巡田 `checkFarm`、土地推送和农场社交事件推送：都调用 `checkFarm` → `runFarmOperation('all')`。
  - 智能有机肥后的跟随收获：`harvestMatureOwnLandsOnce`。
  - 以上都经过小号过滤。手动施肥本身不收获，施肥后的收获是土地推送触发的巡田做的。
  - 手动「收获」「一键全收」走 `doFarmOp`，固定 `propagateErrors=true`，按设计不受限。
  - 好友偷菜 `stealHarvest` 是收别人的地，与此无关。
- **超时起点有隐患（一并修复）。** 原来的超时从服务端成熟阶段的开始时间算起。花费催熟等情况下，这个时间可能远早于作物实际变得可收的时间，10 分钟超时会被判为「已经到了」。另外取不到成熟时间时，访客记录的时间下限是 0，大号很久以前偷过这块地的旧记录也会被当成「已偷」。

#### 修复

- 新增 `core/src/services/fnos-fork-config.ts`：两项设置统一通过 `store.getConfigSnapshot()` 读取，和上游其他设置一样，worker 里按 `FARM_ACCOUNT_ID` 取本账号配置。读取失败会写警告日志，不再静默。
- **超时兜底改为从「本进程首次发现这块地可收」时开始计时**，与服务端的种植或成熟时间戳无关：
  - 换了作物，或者这块地不再可收，计时清零。
  - 程序重启后重新计时（偏保守）。
  - 访客记录只认这一茬作物成熟后的偷菜：取不到成熟时间时，用首次发现可收的时间作为下限。
- **状态日志：**
  - 账号登录完成时打印「小号模式已启用，大号 <昵称>(<GID>)，超时 N 分钟（从本进程首次发现可收时算起）…」或「小号模式未启用」，以及奶茶自动雇佣的启用状态。

- 打开开关后，每 5 分钟检查一次奶茶店空闲的员工位，有空位就雇一个好友（首次检查在启动后约 90 秒）。
- 「雇佣时长」：4 小时 / 12 小时 / 24 小时，或「随机」。
- 「职业」：金牌销售 / 金牌宣传 / 金牌服务 / 默默搬砖，或「不限（随机）」。职业是好友员工自带的天赋，只能按职业挑人，不能指定。
- 「允许雇佣机器人」：默认关闭，只雇真实好友。
- ⚠️ **雇佣会花奶茶券**：4 小时 40、12 小时 130、24 小时 270。券不够时跳过并在日志说明，不会反复重试。
- **当前账号是小号时**（上一张卡片已开启并选了大号），自动切换为小号规则：大号能雇就雇大号 24 小时；大号不能雇（已被别人雇、在冷却、不在可雇名单里）就随机雇一个其他好友 4 小时。下一轮有空位时仍先尝试大号。小号模式下「雇佣时长」设置不生效，「职业」只对随机好友生效、不限制大号。

日志标签：`小号`、`奶茶雇佣`。建议先只留一块成熟地观察日志，确认行为后再放心使用。

#### 判断依据

**「大号偷过」怎么判断**（任一条件满足即可收这块地）：

- 土地作物信息 `PlantInfo.stealers`（字段 14）里出现大号 GID。上游把这个字段声明为 `bytes`（注释「服务端格式不一致」）；其他开源农场项目把它声明为 `repeated int64`（packed varint）。本版两种格式都解析：packed GID 列表，以及旧的 `{gid, num}` 结构，取并集。
- 访客记录（上游已有的 `InteractRecords`）里有大号的「偷取作物」记录（`action_type=1`），地块号 `land_id` 一致，且记录时间不早于这块地成熟时间减 120 秒。只有还有地在等大号时才读访客记录，60 秒内复用结果。

**收获方式：** 有地被留下时，其余可收的地逐块发收获请求（`is_all=false`），被留下的地不收；没有地被留下时与原来完全一样（一次 `is_all=true`）。

**作用范围：** 只限制**自动巡田**（含智能有机肥后的顺带收获）。手动点「收获」「一键全收」不受限制。没开启小号的账号行为与之前完全相同。

**奶茶雇佣：** 复用上游已有的奶茶活动接口（雇佣名单 `hireList`、雇佣 `hire`，上游文档记载已在官方客户端验证过一次员工雇佣），雇佣前沿用上游的校验：候选人可雇（`state=0`）、花费与价格表一致、余额足够、店铺不在结算中。剩余营业时间不够所选时长时，换成能用的最长时长；一个都不够就跳过。

## 5.1 版本号规则（2026.10.19.1 起）

**规则：**

- 版本号 = 构建当天的日期（Asia/Shanghai 时区），写成 `YYYY.M.D`，例如 `2026.10.19`。
- 同一天已经发布过时，依次加第 4 段：第一次重发是 `.1`，然后 `.2`、`.3`……例如 `2026.10.19` → `2026.10.19.1` → `2026.10.19.2`。
- 同一个版本号用于所有地方：
  - `manifest` 的 `version`；
  - Release tag `v<版本>-fnos`；
  - Release 标题「QQ 农场 飞牛原生版 <版本>」；
  - 安装包文件名 `qq-farm-bot_<版本>_native_x86.fpk`；
  - 本文第 5 节的小节标题。
- 不再使用 `V1.x.y`。`V1.0.0` 到 `V1.2.5` 的 Release 保留为历史记录。
- 月和日**不补零**，例如 2026 年 11 月 1 日写成 `2026.11.1`，不写 `2026.11.01`。原因是：已安装的旧版本（如 `2026.10.10`）也是不补零的数字段；而且带前导零的段在某些比较实现里可能被当成字符串或八进制。
- 不使用横杠后缀（如 `2026.10.20-1`）。按语义化版本规则，横杠后面是预发布标记，`2026.10.20-1` 会被视为**低于** `2026.10.20`；Debian 风格的比较结果则相反。两种规则结论不一致，所以 `build.sh` 直接判为格式无效。

**为什么改：** 之前的内部版本是「2026.10.」后面接一个递增计数（`2026.10.0` 到 `2026.10.10`），看起来像日期，其实不是，例如 `2026.10.10` 会被误读成 10 月 10 日。V1.2.5 先把内部版本改成了日期；从 `2026.10.19.1` 起，显示版本也统一用日期，只保留一个版本号。

**比较方式：** 按数字逐段比较，缺少的段视为 0：`2026.10.10` < `2026.10.19` < `2026.10.19.1` < `2026.10.19.2` < `2026.10.20`。第二天按日期生成的版本第三段更大，必然高于前一天任何带 `.N` 的版本。

**`build.sh` 行为：**

- 上次发布的版本取以下两者中较大的一个：
  - 仓库模板 `fnos/qq-farm-bot/manifest` 中的 `version`；
  - 远端仓库（`RELEASE_REMOTE`，默认 `fork`）已有的 `v*-fnos` tag。
  - 远端不可用或离线时，只用模板 manifest。
- 按上次发布的版本自动选号：
  - 上次发布不是今天：用今天的日期 `YYYY.M.D`；
  - 上次发布是今天：在其第 4 段上加 1（`2026.10.19` → `2026.10.19.1`，`2026.10.19.1` → `2026.10.19.2`）。
- 选出的版本写入打包目录中的 `manifest`（仓库模板不会被改动）。
- 可用 `FPK_VERSION=...` 指定版本，必须是 3 到 4 段、不补零的数字。
- 新版本必须严格高于上次发布，否则拒绝构建，以免应用中心不把新包当作升级。本地测试时可设置 `ALLOW_NOT_NEWER=1` 跳过这项检查。
- `VERSION_ONLY=1 fnos/build.sh` 只输出将使用的版本号，不构建。
- 每次发布后，把模板 `manifest` 的 `version` 更新为刚发布的版本。

**`.N` 升级行为（已验证）：**

- 用户已在真实飞牛上实测：应用中心能把第 4 段 `.N`（如 `2026.10.20.3` → `2026.10.20.4`）识别为升级，覆盖安装正常，无需卸载重装。
- 飞牛官方开发文档没有说明版本比较规则；fnpack 1.2.3 也不校验版本格式。以上结论来自实测。
